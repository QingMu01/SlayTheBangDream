# 代码注释规范

本文是**「代码里该不该写这条注释」的唯一事实来源**，适用于 `.cs` 与 `.gdshader`（含 XML 文档注释与 shader 注释）。
新增、修改、清理、评审代码时都按这里判定；设计叙事不归本文管，归 [卡牌](card-authoring.md)、
[机制](mechanic-authoring.md)、[特效](vfx-authoring.md) 三份规范。

## 1. 一条原则

**注释解释「为什么」，不解释「代码在做什么」。** 代码本身已经是最精确的过程说明；
注释只补代码表达不了的东西：外部约束、契约、顺序不变量、数值来源、踩过的坑。

## 2. 四条红线：不写流水线注释

### 2.1 不复述代码与调用顺序

注释把下一行或下一段代码翻译一遍，就是流水账。删掉它，读者不会少任何信息。

```csharp
// ❌ 先记录丢弃数量，再丢弃并补给等量的能量与抽牌。
var count = performCards.Count;
await CardCmd.Discard(choiceContext, performCards);

// ❌ 尚未到达该列的上升起始时间 → 保持隐藏
if (_elapsed < _riseStartTime[i]) { ... }

// ✅ 取消或场景缺失时同步空结果，避免远端一直等待本选项。
```

### 2.2 不写分步流程与箭头时间线

「第一步 / 然后 / 接着 / A → B → C」这类叙述是在代码里重写一遍实现流程，
既和代码重复，又会在改实现时立刻过期。

```csharp
// ❌ 一次性：行点亮 → 扫光 → 提线长出 → 环 + 星 → 光点沿线跑回
var shot = _shot.Value;
var rowsLit = ...;

// ❌ 墨自脚底升过身体、从头顶之上淡出，胸口按下一枚小印，再按元素方向散尽。
```

需要交代整段时间线时，写一句摘要并指向文档：

```csharp
/// <summary>演奏身印：墨带升起 + 胸口小印 + 元素墨迹；设计见 docs/mechanic-authoring.md 12.2。</summary>
```

### 2.3 不把设计散文塞进代码

讲观感、讲「为什么好看」、讲视觉语汇的段落属于 `docs/`。代码里超过 **2 行**的设计论述
一律搬走，只留一句摘要 + 文档锚点。XML 注释同样受此限，`<summary>` 不是散文容器。

判定信号：注释里出现「读成 / 观感 / 之所以 / 视觉事实 / 设计语言」等词，基本就是该搬家的内容。

### 2.4 不留工作过程痕迹

代码不是实验记录。以下内容写进 commit message、`.scratch/` 或 `docs/`，不写进注释：

- `本次` / `实测` / `录帧` / `计划 §x` / `阶段 P3` / `踩坑记录` / `之前是…现在改成…`
- 任务编号（`H-09`）、评审轮次、临时对照实验的结论

可以保留的是**去掉过程后仍然成立的结论**，例如
「画布宽度要盖住 offset + bow，否则波带会从画布侧面凭空出现」。

## 3. 应该写什么

| 类型 | 例子 |
|---|---|
| 非显然的外部约束 | `// 波前用时必须与卡牌的 WithWaitBeforeHit 对齐，否则先掉血后看见波。` |
| 顺序 / 不变量 | `// 身印与槽位几何无关，放在槽位布局判定之前。` |
| 数值来源与单位 | `/// <summary>身体框设计基准（Sakiko %Bounds 320×300），其余角色按比例换算。</summary>` |
| 踩坑结论（写成普适条件） | `// 拖尾前缘要埋进球体，落在球心上会画出一条硬分界。` |
| 为什么不用更直观的写法 | `// 材质是 local_to_scene，改它不会污染其他实例。` |
| 公共契约 / 参数语义 | `/// <param name="preload">是否随战斗预载。</param>` |

格式要求：

- 一句话能说清就写一行；不要为凑格式拆成多行。
- 同一处的行内注释块不超过 2 行；需要更多空间说明「为什么」，说明它该进 `docs/`。
- 公共 API 的 `<summary>` 用一句话交代职责与关键约束，不写实现步骤。

## 4. 写完自检（三问）

1. **删掉这条注释，读者会误解代码吗？** 不会 → 删。
2. **它在描述「做了什么」还是「为什么 / 什么约束」？** 前者 → 删或改写。
3. **它超过 2 行、在讲设计或观感吗？** 是 → 搬进 `docs/`，代码留一句摘要 + 指路。

三个问题里任何一问的答案是「该删 / 该搬」，就按它处理。

## 5. 清理一段分支区间的注释

```bash
# 1. 列出区间内的提交，确认起点
git log --oneline <base>..HEAD

# 2. 列出新增的注释行，逐条按 §2 判定
git diff -U0 <base>..HEAD -- '*.cs' '*.gdshader' | grep -E '^\+\s*(//|/\*|\*)'

# 3. 收尾确认：编辑未提交时用 git diff HEAD，已提交时用 git show HEAD。
#    输出应只剩以 * 开头的块注释续行（算式续行也以 * 开头，逐条确认）；
#    出现其他行说明改到了代码
git diff HEAD -- '*.cs' '*.gdshader' \
  | grep -E '^[+-]' | grep -vE '^(\+\+\+|---)' \
  | grep -vE '^[+-]\s*//' | grep -vE '^[+-]\s*$' | grep -vE '^[+-]\s*/\*'
```

口径：

- **保留**契约、时序耦合、不变量、踩坑结论；**删除**复述、分步流程、设计散文、过程痕迹。
- 长设计说明不是删掉，而是确认它已在 `docs/` 有落点，再在代码里留一句摘要 + 章节号。
- 不顺手改行为、不动 `docs/` 里的设计记录、不把有意义的一行摘要也一起删光。
- 验收：纯注释 diff、两个项目构建通过、架构检查 0 HARD；改到 shader 时补一次无头加载。

历史口径可对照 `423b8ab`（流水账）、`8be1f29`（冗余步骤）、`ded2298`（全面精简）、
`a3ad8e7`（演奏印框 / 震荡特效）。

## 6. 边界

- 本文只约束**代码注释**；`docs/` 允许且鼓励完整的设计叙事。
- grep 只用于提候选，不能把命中数当违规数：箭头、`本次`、`阶段` 等词在契约描述里也可能合法
  （如「锁内快照 → 锁外 hook → 锁内提交」），必须逐条读语义再判。
- 生成代码、第三方代码、`addons/` 不套用本文。
